## Notes and decisions

1. Sign-in feeds. The v1.0 /auditLogs/signIns endpoint returns only interactive user sign-ins ("Sign-ins that are interactive in nature... are currently included in the sign-in logs"). The signInEventTypes property and its filter exist only on the beta endpoint. The non-interactive feed therefore uses beta with the filter `signInEventTypes/any(t: t eq 'nonInteractiveUser')`, which is the query Microsoft's own monitoring documentation prescribes. SPEC section 4 permits beta when a dataset requires it; this is that case. The interactive feed stays on v1.0 because it does not require beta. Both feeds use a `createdDateTime ge {UTC start}` filter for the collection window (default 30 days, --days flag) as the v1.0 docs recommend to avoid timeouts.

2. Sign-in CA data. appliedConditionalAccessPolicies is included in sign-in events only when the app holds Policy.Read.All, Policy.Read.ConditionalAccess, or Policy.ReadWrite.ConditionalAccess in addition to AuditLog.Read.All. This app's manifest includes Policy.Read.All, so the field is present. (Source: signin-list permissions section.)

3. userRegistrationDetails permission. Current docs list AuditLog.Read.All as the application permission for GET /reports/authenticationMethods/userRegistrationDetails. The SPEC section 3 manifest assigns this dataset to Reports.Read.All; the manifest is the contract and both permissions are requested, so collection works either way. The verify command uses this endpoint as the representative check for Reports.Read.All; note that a tenant could pass that check through AuditLog.Read.All alone.

4. users paging with signInActivity. When $select includes signInActivity the maximum page size is 500 (the collector requests $top=500); without it the maximum is 999. signInActivity requires an Entra ID P1 or P2 license and is not returned for users who never signed in or last signed in before April 2020. (Source: user-list optional query parameters.)

5. PIM eligibility readability. roleEligibilitySchedules is on v1.0 and RoleManagement.Read.Directory appears in its accepted permission list, so eligibility should be readable with this manifest. If the call fails anyway (for example a tenant without PIM), the roles collector stores roleEligibilitySchedules as null with roleEligibilityStatus "unknown" per SPEC section 4, and the collect is not marked partial for that.

6. servicePrincipals paging. Default and maximum page size is 100; the collector relies on @odata.nextLink rather than $top. Listing servicePrincipals may also return agentIdentityBlueprintPrincipal objects (distinguished by @odata.type); they are stored as returned.

7. P2 detection. Entra ID P2 is detected by the presence of service plan AAD_PREMIUM_P2 (servicePlanId eec0eb4f-6444-4f95-aba0-50c24d67f998) in any subscribed SKU's servicePlans, by id or by name. Verified against the licensing service plan reference (learn.microsoft.com/entra/identity/users/licensing-service-plan-reference): this service plan id appears identically inside Entra ID P2 (SKU 84a661c4-e949-4bd2-a560-ed7766fcaf2b), EMS E5, Microsoft 365 E5, and the other P2-bearing bundles, so checking the service plan rather than SKU ids covers all of them. These GUIDs are universal constants and are never transformed by the sanitizer.

8. riskyUsers without P2. The riskyUsers API requires a P2 license per its docs. The collector checks subscribedSkus first and writes a skip marker instead of calling the API when P2 is absent. The verify command still calls it once; a license-related error is reported as WARN, not FAIL, because it does not indicate missing consent.

9. groups transitive member counts. /groups/{id}/transitiveMembers/$count requires the advanced query parameters (ConsistencyLevel: eventual header); the response is a text/plain integer. Counts are fetched only for group ids referenced by CAP policy include/exclude lists, auth method includeTargets/excludeTargets, and the registration campaign targets, and only when the id exists in the tenant's group list (a CAP exclusion GUID can be a user, not a group).

10. Config file format. SPEC section 2 mandates config.yaml but the exclusive dependency list contains no YAML library. config.py implements the small YAML subset the config uses (scalar strings plus one nested mapping, comments tolerated). The file remains valid YAML readable by standard tools.

11. Snapshot directory timestamps. SPEC section 5 specifies an ISO 8601 timestamp in the path. Windows forbids ":" in paths, so the basic format without separators is used (for example 20260610T031500Z), which is valid ISO 8601.

12. Sanitizer scope decisions. (a) appId values are never transformed anywhere, not only known first-party ids: appIds are global application identifiers, not tenant data, and the engine compares applications by appId. (b) Policy, auth strength, named location, role, and service principal display names are kept readable because they are structure the operator needs; user display names (including userDisplayName in sign-ins and reports) and group display names are pseudonymized. (c) IPv6 addresses map into 2001:db8::/32, the IPv6 documentation range; SPEC names only the IPv4 ranges. (d) Each distinct verified domain maps to its own token (tenant.example, tenant2.example, ...) to preserve distinctness; emails all map to user{N}@tenant.example. (e) The sanitizer raises an error past 508 distinct IPv4 addresses rather than reusing tokens, preserving the distinctness guarantee.

13. MSAL certificate credential. msal.ConfidentialClientApplication accepts {"private_key": PEM, "thumbprint": SHA-1 hex} as client_credential; the thumbprint is computed from the generated certificate at load time. Authority is https://login.microsoftonline.com/{tenantId}. The only outbound hosts are graph.microsoft.com (enforced by an allowlist in graphclient) and login.microsoftonline.com (MSAL token endpoint).

Recorded fixtures in tests/fixtures/ are synthetic sanitized snapshots authored to match the documented response shapes on Microsoft Learn (no live tenant existed at M0 build time). They use only documentation values: tenant.example, 203.0.113.0/24, placeholder GUIDs, plus genuine universal constants (role template ids, first-party appIds, SKU and service plan ids). After the first live collect and sanitize, fixtures can be replaced with real sanitized snapshots.

See note 35.**
   Delegated scopes requested during device code flow: Application.ReadWrite.All, AppRoleAssignment.ReadWrite.All. The operator must be a Global Administrator of the golden tenant. 17. Microsoft Graph service principal appId. The universal constant appId for the Microsoft Graph first-party service principal is 00000003-0000-0000-c000-000000000000. This is the same in every Entra tenant. The object ID of its service principal differs per tenant and is fetched dynamically in setup. (Source: known Microsoft constant; confirmed stable across tenants by Microsoft documentation.)

15. Snapshot normalization of string arrays. store.sort_collections() sorts all homogeneous string arrays (lists where every element is a string) in addition to sorting object arrays by id. This means fields like builtInControls, clientAppTypes, allowedCombinations, countriesAndRegions, and includeApplications/excludeApplications (when they contain appId strings rather than the "All" / "Office365" tokens) are stored in sorted order. The parity engine (M1) must treat these fields as sets and compare sorted representations; the snapshot normalization guarantees the stored form is already sorted, so set equality reduces to string equality after canonicalization.

19. signIns pulls must use bounded one-day windows. GET /auditLogs/signIns supports $top, $skiptoken, and $filter; the maximum and default page size is 1,000, and the docs themselves advise a time-range $filter "to avoid having the request time out", with their own example using a bounded ge/le range (Source: signin-list, graph-rest-1.0, verified 2026-07-02). Measured live 2026-07-02 against a real tenant: the backend's per-request cost scales with scan window times page fill target, and results vary wildly between runs. With a 30-day unbounded-above filter: no $top -> Graph 504s at its ~120s gateway limit; $top=500 -> never answered within 90-180s; $top=250 -> once succeeded at 77s, and $top=999 on the beta feed once returned a page in 14s and later 504d on the identical query. With a one-day bounded [ge, lt) window: $top=999 returned the entire day in one page in ~5-7s on both feeds (137 events beta, 13 events v1.0), reliably. Consequences: the collector pulls each feed in one-day createdDateTime slices, oldest first, the newest slice unbounded above, $top=999, each slice a small independently-retried request; the GraphClient default read timeout is 180s (above Graph's own ~120s limit) so slow successes and retryable 504s arrive instead of opaque client ReadTimeouts. The test mocks for both signIns routes return 504 when $top is absent, serve the fixture on the unbounded newest slice, and return empty pages for bounded slices. The verify probe for AuditLog.Read.All sends $top=1 unfiltered and is unaffected.

20. First-party application classification and composite ids in sanitize. Microsoft first-party service principals are owned by the Microsoft Services tenant f8cdef31-a31e-4b4a-93e4-5f571e91255a or the Microsoft Corporation tenant 72f988bf-86f1-41af-91ab-2d7cd011db47 (Source: learn.microsoft.com troubleshoot article "Verify first-party Microsoft applications in sign-in reports", verified 2026-07-02). The sanitizer preserves an appId only when the snapshot's own service principal list shows one of those owner tenants, or the id matches the documented first-party GUID families (x-0000-0ff1-ce00-000000000000 Office 365 workloads; x-0000-0000-c000-000000000000 classic Microsoft services, for example Microsoft Graph 00000003-0000-0000-c000-000000000000). Tenant-created appIds map to stable pseudonyms, so canonical appId comparison still holds inside a sanitized snapshot. Separately, subscribedSku.id is observed live to be the composite "{tenantId}_{skuId}" (the resource doc calls it only "unique identifier"; confirmed against a real tenant 2026-07-02), so the sanitizer also pseudonymizes GUIDs embedded inside longer strings, preserving embedded universal constants (SKU GUIDs, role template ids, first-party appIds). Found because the first live sanitize leaked the real tenant id inside the subscribedSku id and the collector's own appId in service_principals.json; both are covered by m0 regression tests.

18. roleDefinitions query parameters. GET /roleManagement/directory/roleDefinitions supports only $filter (eq and in operators, on id, displayName, and isBuiltIn) and $expand. It does not support $top; live Graph returns 400 Request_UnsupportedQuery (observed against a real tenant 2026-07-02, which the original verify probe's $top=1 triggered). The verify probe now filters on id eq the Global Administrator role template ID 62e90394-69f5-4237-9190-012177145e10, a universal constant present in every tenant, returning exactly one object. The roles collector is unaffected: it sends no query parameters and follows @odata.nextLink only. The test mock for this endpoint rejects $top with 400 to match live behavior. (Source: rbacapplication-list-roledefinitions, graph-rest-1.0, verified 2026-07-02.)

24. Entra behaviors verified for the SPEC-PUBLIC default basics pack (verified 2026-08-14 against learn.microsoft.com). These are product behaviors rather than Graph shapes, but they determine what the pack may safely recommend, so they are recorded here before any of it is coded. (a) Mandatory multifactor authentication for the Azure portal, Entra admin center, and Intune admin center is enforced at the client application level and is not tied to Conditional Access; excluding an account from every Conditional Access policy therefore does not exempt it from that prompt. Consequence: a password-only emergency access account cannot reach the Entra portal during the emergency it exists for, so the pack requires emergency access accounts to carry a phishing-resistant method (passkey or certificate-based authentication) that differs from the method normal admin accounts use, while still being excluded from Conditional Access policies that could block sign in. (Sources: entra/identity/role-based-access-control/security-emergency-access; entra/identity/authentication/concept-mandatory-multifactor-authentication.) (b) The Conditional Access persistent browser session control requires the policy to target all cloud applications and cannot be scoped to a subset, so "persistent sessions for non-admins" is necessarily its own policy with admins excluded. The legacy "remember multifactor authentication on trusted devices" setting should be disabled before using sign-in frequency, since combining them produces prompts at unexpected times. (Sources: entra/identity/conditional-access/howto-conditional-access-session-lifetime; entra/identity/conditional-access/concept-conditional-access-session; entra/identity/conditional-access/policy-all-users-persistent-browser.) (c) Windows Hello for Business is inherently multifactor, so sign-in with it issues a Primary Refresh Token carrying the multifactor claim and that token provides silent single sign on for its lifetime. There is no Windows Hello setting that makes multifactor "satisfied indefinitely"; the behavior comes from the PRT plus the absence of an aggressive sign-in frequency on that population. Confirmed against this project's own live data: windowsHelloForBusiness appears in the allowedCombinations of the built-in Phishing-resistant MFA strength (id 00000000-0000-0000-0000-000000000004) observed in snapshot 20260814T164130Z, so requiring phishing-resistant methods and using Windows Hello are the same requirement, not competing ones. (d) The Conditional Access condition is named "Authentication flows" and has exactly two options, "Device code flow" and "Authentication transfer"; there is no "device auth flow". The existing pack already models both correctly (cap-004 device code, cap-003 transfer) and only the user-facing vocabulary needed correcting. Still to verify before the items that depend on them are coded, per the CLAUDE.md rule: the Microsoft Authenticator passkey AAGUID values for iOS and Android (needed because AAGUID key restrictions silently block Authenticator passkeys while security keys keep working), and the current state of the migration from the legacy separate MFA and SSPR method policies to the converged Authentication methods policy.

25. PUB-M2 pack control shapes, verified against Microsoft Learn 2026-08-14 before any control was authored. Four of these contradict what the shapes were assumed to be, and each would have shipped a control that silently never matched. (a) Session controls (v1.0 conditionalAccessSessionControls): signInFrequency is {isEnabled, type: days|hours, value: Int32, authenticationType: primaryAndSecondaryAuthentication|secondaryAuthentication, frequencyInterval: timeBased|everyTime}; "every time" is frequencyInterval everyTime, with type and value not meaningful in that form. persistentBrowser is {isEnabled, mode: always|never} -- **mode is always/never, not single/never**. The all-apps constraint is documented twice: the Graph reference says "All apps should be selected for this session control to work correctly" and the portal how-to says the control requires selecting All Cloud Apps because all tabs in a browser session share one session token. The docs state the requirement but do not say the API rejects the policy, so the control treats it as a posture warning rather than a validation error. (b) conditions.authenticationFlows is {transferMethods: String} -- **a single comma-joined flags string, not an array**: both flows set reads "deviceCodeFlow,authenticationTransfer", so it is parsed by splitting on comma. Values none|deviceCodeFlow|authenticationTransfer. (c) conditions.devices.deviceFilter is {mode: include|exclude, rule: String} where rule is free-text Entra dynamic-membership syntax with no structured breakdown; v1.0 conditionalAccessDevices exposes only deviceFilter. (d) FIDO2 config (authenticationMethodConfigurations/FIDO2): isAttestationEnforced (Boolean) and keyRestrictions {isEnforced, enforcementType: allow|block, aaGuids[]} are **both marked deprecated in v1.0, removal October 2027, replaced by passkeyProfiles**, a collection of {id, name, passkeyTypes: deviceBound|synced, attestationEnforcement: disabled|registrationOnly, keyRestrictions{...}} where attestation becomes a three-value enum rather than a Boolean. Both shapes are live today, so a control reads passkeyProfiles when present and falls back to the tenant-level legacy fields. (e) Microsoft Authenticator passkey AAGUIDs, published by Microsoft: Android de1e552d-db1d-4423-a619-566b625cdc84, iOS 90a3ccdf-635c-4729-a248-9b709135078f. These must appear in an allow-type keyRestrictions list or Authenticator passkeys are silently blocked while security keys keep working. (f) Temporary Access Pass config: {state, defaultLifetimeInMinutes, defaultLength, minimumLifetimeInMinutes, maximumLifetimeInMinutes, isUsableOnce, includeTargets, excludeTargets}; length 8-48, lifetimes 10-43200 minutes. **"Who may issue a TAP" is not a policy field at all**: includeTargets is who may sign in with one. Issuance is RBAC (Privileged Authentication Administrator, Authentication Administrator), so any control claiming to check it must read role assignments, not this policy. (g) Registration campaign (registrationEnforcement.authenticationMethodsRegistrationCampaign): {state: default|enabled|disabled, snoozeDurationInDays 0-14, includeTargets[{id, targetType, targetedAuthenticationMethod}], excludeTargets[{id, targetType}]}; snooze 0 prompts on every MFA attempt. **enforceRegistrationAfterAllowedSnoozes is beta only** and absent from the v1.0 property table, so it is never read from a v1.0 response. (h) authenticationMethodsPolicy.policyMigrationState is in v1.0: premigration | migrationInProgress | migrationComplete | unknownFutureValue, and **only migrationComplete means the legacy MFA and SSPR policies are actually ignored**. (i) Security Defaults: GET /policies/identitySecurityDefaultsEnforcementPolicy, field isEnabled. (j) Standing privileged access is three endpoints, not one field: roleAssignments carries no time or type field and cannot distinguish permanent from PIM-activated; roleAssignmentSchedules carries assignmentType Assigned (standing) vs Activated (temporary elevation) plus scheduleInfo; roleEligibilitySchedules is eligible-only. The correct read for standing access is roleAssignmentSchedules filtered to assignmentType eq 'Assigned' with no expiry in scheduleInfo -- **using roleAssignments alone counts in-flight PIM activations as permanent**. The documented sample for roleAssignments also returns an undocumented resourceScope property that must not be depended on. (k) Risk conditions: signInRiskLevels and userRiskLevels are required riskLevel collections (expect [] rather than absent) with values low|medium|high|hidden|none|unknownFutureValue; hidden is a real value and easy to miss. servicePrincipalRiskLevels has no hidden, and insiderRiskLevels is a single String rather than a collection. (Sources: graph-rest-1.0 reference pages for signInFrequencySessionControl, persistentBrowserSessionControl, conditionalAccessSessionControls, conditionalAccessAuthenticationFlows, conditionalAccessFilter, conditionalAccessDevices, fido2AuthenticationMethodConfiguration, fido2KeyRestrictions, passkeyProfile, temporaryAccessPassAuthenticationMethodConfiguration, authenticationMethodsRegistrationCampaign v1.0 and beta, authenticationMethodsPolicy, identitySecurityDefaultsEnforcementPolicy, unifiedRoleAssignment, unifiedRoleAssignmentSchedule, unifiedRoleEligibilitySchedule, conditionalAccessConditionSet; plus entra/identity/conditional-access/howto-conditional-access-session-lifetime, entra/identity/authentication/how-to-enable-authenticator-passkey, entra/identity/authentication/howto-authentication-temporary-access-pass.)

27. Four pack controls were removed or rewritten on 2026-08-14 because no source supported them and one contradicted the pack itself. They shared a symptom: a mechanically derived canonical form with boilerplate rationale text, which is the same "grade the shape, not the effect" fault that stalled the engine in July, surviving in the data rather than the code. (a) **method-X509Certificate required certificate-based authentication disabled** with the rationale "this method is easier to trick or intercept". Neither source supports that for CBA. SCuBA MS.AAD.3.1v1 names Entra CBA as one of four recommended phishing-resistant methods and notes it supports federal PIV card authentication; Microsoft's authentication strengths table shows CBA (multifactor) satisfying all three built-in strengths including phishing-resistant. The pack was also internally inconsistent, since strength-002 and strength-003 both list x509CertificateMultiFactor as an allowed combination and cap-001 and cap-002 grant on it. Removed: a tenant with a PKI has made a deliberate choice and grading it down was a false finding, while requiring CBA of a tenant without a PKI would be absurd. (b) **method-VerifiableCredentials** carried the same boilerplate rationale with no source at all. Removed. (c) **method-SoftwareOath required the method enabled** with a rationale that describes no verifiable standard ("set up the way the standard expects"). No framework requires it on, and requiring it points against the phishing-resistant direction of the pack's own cap-001 and cap-002. Removed. (d) **method-QRCodePin required the method disabled.** Microsoft does not say to turn it off. It says it is off by default, that it is single-factor, that it is meant for frontline workers rather than information workers, and "don't enable QR code authentication for all the users in your tenant" -- that is, scope it. A blanket requirement failed a correctly scoped frontline deployment. Rewritten as a conditional control that applies only when the method is enabled and requires that it not target all users, which needed a new excludes predicate and a derived includeTargetIds field on the authMethods observation. (e) **method-TemporaryAccessPass** was not removed but its rationale contradicted its own check: the text argued for a single use pass while the canonical required isUsableOnce false. The lifetime and length bounds are the security control; single use is an operational trade Microsoft documents (a one-time pass forces reissue because passwordless registration must complete inside ten minutes). The rationale was corrected and single use now passes as stricter.

28. Two conflicts between the pack and published guidance are deliberate and must never be presented as framework coverage. (a) **session-003 requires an always-persistent browser session**, and Microsoft's Conditional Access template is literally named "No persistent browser session", with the underlying article setting persistent browser to Never persistent alongside a one-hour sign-in frequency and warning that persistent cookies "can create a security vulnerability by allowing unauthorized access". The operator's decision, recorded 2026-08-14: MFA fatigue is itself a security risk because people become numb to the prompts and stop reading them, and the people using this tool have to care about that where end users do not. Partial reconciliation: Microsoft's template is scoped to unmanaged or non-compliant devices, whereas this control is unscoped by device. No honest "meets" claim exists for it against any framework, so it carries a Microsoft article citation for context and no policy citation. (b) **cap-005 blocks legacy authentication with no exclusions**, while Microsoft's article recommends excluding at least one account to avoid lockout. This is the only Conditional Access control in the pack with no emergency-account exclusion. It is kept stricter deliberately: an emergency access account has no need of legacy authentication, and an exclusion here is a standing hole in the one control that closes the oldest protocols.

29. Two operational traps recorded for later, both from the 2026-08-14 research and neither yet handled in code. (a) The registration campaign article's limitations state the passkey nudge is suppressed when the passkey profile has attestation enforced or AAGUID restrictions applied. Both method-Fido2 (isAttestationEnforced true) and method-Fido2-aaguid describe exactly that, so **passing those two controls can silently defeat campaign-001**, and the pack currently cannot see the interaction. (b) Email one-time passcode "can't be disabled" while the separate B2B setting allowing external users to use email OTP is enabled, so a tenant using guest email OTP may be structurally unable to satisfy method-Email while retaining guest access; that belongs with the guest and cross-tenant work still open in PUB-M2b. Also time-bound: legacy ID Protection risk policies retire 1 October 2026, and strict-001 encodes the older "Require password change" control where Microsoft's current guidance is "Require risk remediation", which auto-applies an authentication strength and a sign-in frequency of every time.

Guest, consent and default user permission shapes, verified 2026-08-14 against Microsoft Learn and against ScubaGear release v1.8.0 read from the cisagov/ScubaGear repository at tag v1.8.0 (commit 2d01e711fcb74f615e1fbea6d06556a8dcbff11f, confirmed via the GitHub API against ScubaGear.psd1). (a) **guestUserRoleId** role template ids, confirmed identically on two Microsoft pages: User, meaning the same access as a member, a0b1b346-4d3e-4e8b-98f8-753987be4970; Guest User, the tenant default, described as limited access, 10dae51f-b6af-4016-8d66-8c2a99b929b3; Restricted Guest User, labelled most restrictive in the portal, 2af84b1e-32c8-42b7-82bc-daa82404023b. SCuBA MS.AAD.8.1v1 (SHOULD) accepts either of the latter two, and its Rego fails only the member-equivalent value. Microsoft's Zero Trust guidance recommends restricted, but the restrict-guest-permissions article lists services that do not support it, naming Forms, Project Online, Viva Engage and Planner in SharePoint, so guest-001 grades only the member-equivalent value as a finding. (b) **allowInvitesFrom** v1.0 values, most to least permissive: everyone (the default outside US Government), adminsGuestInvitersAndAllMembers, adminsAndGuestInviters, none (the US Government default). **ScubaGear v1.8.0 fails any value other than adminsAndGuestInviters, including none**, so a tenant on the strictest possible setting fails MS.AAD.8.2v1; that logic is deliberately not copied, since grading a tenant down for exceeding the standard is the conservative rule inverted. (c) **permissionGrantPoliciesAssigned** encodes user consent as ManagePermissionGrantsForSelf.{id} entries, and an empty list means user consent is disabled. Three gotchas, all load bearing: the documented v1.0 GET example returns capital-M ManagePermissionGrantsForSelf while the PATCH examples use lowercase, so comparison is case insensitive; the same collection also carries ManagePermissionGrantsForOwnedResource.* entries, which are Teams chat and team scoped grants and are not the user consent setting; and a tenant may point at a policy id that is not one of the published built-ins, which is not hypothetical, see note 31. (d) **adminConsentRequestPolicy is generally available in v1.0**, a singleton at /policies/adminConsentRequestPolicy carrying isEnabled, notifyReviewers, remindersEnabled, requestDurationInDays, reviewers and version. This is preferred over the older directory setting EnableAdminConsentRequests in the Consent Policy Settings template (id dffd5d46-495d-40a9-8e21-954ff55e198a), which ScubaGear uses and which is beta only: that template may legitimately not exist until something writes to it, so it cannot distinguish an unconfigured tenant from an untouched one, and it does not carry the reviewer list. A consequence to expect: output may differ from ScubaGear on edge-case tenants, and no Microsoft document states the two surfaces share a store. (e) **allowUserConsentForRiskyApps** is recommended false by the v1.0 reference in as many words, is inverted relative to the directory setting BlockUserConsentForRiskyApps that backs it, and **the documented GET example returns null**, which the live lab tenant also returns. Null means never explicitly set, which behaves as the safe default, so riskyapps-001 does not apply rather than failing; reading null as false would invent a finding on most tenants alive. (f) **allowedToReadOtherUsers is deliberately never graded.** The Graph reference says, in bold, do not set this value to false, and the default-permissions article says setting it false might prevent reading user information in other Microsoft services like Teams and is not recommended. A hardening control that breaks what it protects is not hardening. (g) **allowedToCreateSecurityGroups has no verified recommendation** from Microsoft or SCuBA and is not graded. (h) **blockMsolPowerShell is not graded.** The only Microsoft page instructing that it be set is scoped to education tenants and School Data Sync, and is framed as how to block rather than as a recommendation. A search result claiming it breaks Entra Connect contradicts the Graph reference, which states it does not affect Entra Connect or Microsoft Graph, and could not be verified from a Microsoft source, so it is not encoded either way. (i) SCuBA policies that map here, all last modified June 2023: MS.AAD.5.1v1 SHALL, only administrators may register applications; MS.AAD.5.2v1 SHALL, only administrators may consent to applications; MS.AAD.5.3v1 SHALL, an admin consent workflow SHALL be configured; MS.AAD.8.1v1 SHOULD, guests limited or restricted; MS.AAD.8.2v1 SHOULD, only guest inviters may invite. MS.AAD.8.3v1, restricting invites to named external domains, is marked Should/Not-Implemented in ScubaGear itself and always returns not met, so it is not mapped. Note MS.AAD.5.2v1 fails the verified-publisher setting Microsoft itself recommends, which is why the pack splits user consent across the baseline and strict profiles and cites the policy only against the strict one.

31. **Per user legacy MFA state is not readable from Graph v1.0 and is therefore not in the pack.** Three independent confirmations: the strongAuthenticationRequirements resource carries a single beta moniker with no v1.0 counterpart link, unlike every v1.0 page checked alongside it; the v1.0 authentication resource's relationship table has no requirements relationship, so /v1.0/users/{id}/authentication/requirements has no route; and Microsoft's own migration guidance states that isMfaCapable in the registration report "is not the exact equivalent of StrongAuthenticationRequirements" because it does not distinguish disabled, enabled and enforced, naming perUserMFAState as the exact equivalent and calling it through /beta/$batch. The v1.0 userRegistrationDetails property list carries no enforcement-state field of any kind. Reading it would mean a beta dependency Microsoft does not support in production plus a per-user call, so the honest answer is that this control is not implementable under a v1.0-only policy, and approximating it with isMfaCapable would report a different question's answer.

32. The two consent policy ids the live tenant carries, researched 2026-08-15 after the pack passed a tenant that plainly allowed user consent. Verified from the docs source repository MicrosoftDocs/entra-docs, file docs/identity/enterprise-apps/manage-app-consent-policies.md, cross checked against the rendered Learn page. **microsoft-user-default-recommended** is described as "Permissions consentable based on Microsoft's current recommendations" and is the policy behind the portal option "Let Microsoft manage your consent settings". It is the default for new tenants and it is Microsoft managed, meaning its contents change without the id changing. It is **not** a rename of microsoft-user-default-low and carries no verified publisher condition and no permission classification condition: its stated rule is that end users can consent to any user consentable delegated permission except a named list of roughly thirty six Graph and Exchange Online permissions covering mail, files, sites, calendars, contacts, tasks, chat and online meetings. That is allow everything minus a deny list, which is architecturally the successor to the permissive legacy policy rather than to the restrictive one. **microsoft-user-default-allow-consent-apps** is described as "Popular mail clients consentable for users" and re-permits exactly those held back mail permissions, but only for six named client applications (Apple Mail, Spark, eM Client, Android-Samsung, Android-Mail, Thunderbird). It is enabled by default alongside the recommended policy. Microsoft's own Mail client policy section writes the id with two words transposed; the built in list and live tenants both use the order recorded here. **Assigned policies compose as a union**: the documentation states each policy is evaluated separately, an exclusion in one does not affect inclusions in another, and a user needs only one policy to allow an action. So the two together mean a user may consent to mail permissions for those six clients even though the first policy excludes them. Two consequences for this pack. First, the older configure-user-consent article still documents only microsoft-user-default-low and microsoft-user-default-legacy and does not mention either new id, so the two Microsoft articles are internally inconsistent and the newer one governs. Second, **ScubaGear v1.8.0 reports MS.AAD.5.2v1 as met on a tenant in this state**: its Rego string matches only the legacy and low ids, so a tenant on the managed default produces an empty bad-policy set and passes while non-admin user consent is demonstrably on. CISA tracks the underlying question as cisagov/ScubaGear issue 1859. This pack deliberately differs, which is why consent-002 rather than consent-001 carries the MS.AAD.5.2v1 citation, and why consent-001 is an allow list of ids known to be restrictive rather than a deny list of ids known to be bad. The finding text says the tenant is on Microsoft's managed default rather than implying it is wide open, because the sensitive permissions genuinely are held back and overstating it would be as wrong as missing it.

Which tenant proves what, corrected 2026-08-15 after the operator pointed out that the earlier version of this note described the wrong one. **Golden is the tenant that exercises the pack.** Security defaults is off, which is what allows Conditional Access to run at all, and it carries ten Conditional Access policies, twelve users, nine groups, four licence SKUs including Entra ID P2, and two Global Administrators: the operator's everyday account and a separate emergency account. Grading it against the basics pack runs all thirty applicable controls with no unknowns, so the Conditional Access, session, strength and strict halves of the pack are proven against live data rather than only against fixtures. That is still worth having, because it is what a small unconfigured tenant looks like and it is the shape most self-hosting readers will point this at first, but it proves nothing about the policy half. 35. Setup privilege reduction, verified 2026-08-15 against the Microsoft Graph permissions reference (learn.microsoft.com/graph/permissions-reference). The device-code setup token was requesting Application.ReadWrite.All and AppRoleAssignment.ReadWrite.All. Both were reduced. (a) **Application.ReadWrite.All to Application.ReadWrite.OwnedBy.** The reference confirms OwnedBy "allows the app to create other applications, and fully manage those applications ... It cannot update any apps that it is not an owner of," and that the creating principal becomes an owner automatically, which is exactly what setup needs: create the one Collector app and its service principal, nothing else. .All additionally allows rewriting any application or service principal in the tenant, which setup never does. (b) **AppRoleAssignment.ReadWrite.All is dropped entirely, not lowered.** The reference confirms it is the only permission that grants app-role assignments (there is no OwnedBy variant) and warns that permissions like it "allow an application to grant additional privileges to itself, other applications, or any user." Rather than hold the one scope Microsoft flags as self-escalating, setup no longer grants consent programmatically at all: it creates the app with its requiredResourceAccess set to the ten read roles, then prints the tenant admin-consent URL (login.microsoftonline.com/{tenantId}/adminconsent?client_id={appId}) for the signed-in Global Administrator to approve through Microsoft's own screen. That consent runs under the administrator's directory role, needing no token scope, and it is the same mechanism already used to consent a second tenant. Net effect: the setup token carries a single owned-app scope, the administrator approves read-only access on Microsoft's own consent page, and the persistent Collector credential remains read-only as before. A test asserts the reduced scope set and that AppRoleAssignment is never requested.

36. Collector certificate lifetime and renewal, decided 2026-08-15. The certificate is the one standing credential that authenticates headless to every configured tenant, so its validity period is the window a stolen copy stays useful. Lifetime was cut from 730 days to 180 (CERT_LIFETIME_DAYS), on the operator's ruling that a posture read is periodic rather than continuous, so re-running setup twice a year is a small price for halving the exposure window. make_client checks the certificate on every live-Graph command through that one chokepoint: past expiry it stops with an instruction to re-run setup rather than letting a lapsed credential surface as an opaque authentication failure inside a collect, and within CERT_RENEW_WARNING_DAYS (21) it warns so renewal happens on the operator's schedule. The full delegated-only alternative (no persistent credential at all, re-auth every pull) was considered and declined because it would remove the unattended, scheduled collection an MSP running this across many tenants relies on; the app-plus-short-cert model keeps that while bounding the credential's life.
